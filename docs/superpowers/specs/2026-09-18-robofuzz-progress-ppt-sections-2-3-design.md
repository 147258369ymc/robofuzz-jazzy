## 4. 统一视觉规范

### 4.1 页面与字体

- 比例：16:9，`33.867 × 19.05 cm`。
- 主字体：微软雅黑；Linux 渲染时允许回退为 Noto Sans CJK SC。
- 页面标题：32 pt、加粗、黑色；长标题必要时可降到 30 pt，但不可小于 30 pt。
- “主要难点”标签与正文：24 pt、加粗。
- “方法 / 创新”正文：20 pt、加粗；若自然句较长，可降到 18 pt，但不得继续缩小。
- 中央技术图主节点：18—22 pt。
- 中央技术图辅助说明：15—16 pt。
- 表格表头：14 pt、加粗；主体不低于 11.5 pt。

### 4.2 配色

- 主深蓝：`#002060`。
- 目录编号与流程主蓝：`#0070C0`。
- 标题分隔线：`#6592F5`。
- 表格首行：`#00B0F0`。
- 难点和关键动作：`#C00000`。
- 语义变异、反馈映射和下一阶段分支：橙色 `#EF962D`。
- 已形成验证能力：绿色 `#289D64`。
- 辅助结果区：浅灰 `#F3F6F8`。
- 风险、越界口径和偏轨强调：红色 `#C00000`。

### 4.3 框体和箭头

- 中央技术图只使用直角矩形，不使用圆角卡片。
- 主节点使用 2—3 pt 黑色、蓝色、橙色或绿色实线边框。
- 主流程严格从左到右，使用实线单箭头。
- 外层闭环或返回种子队列的反馈线沿节点外围走正交折线，用绿色虚线表示；反馈处理链内部使用绿色实线。
- 反馈到具体变异策略的局部映射使用橙色虚线，与外层闭环区分。
- 下一阶段或尚未完成的分支使用橙色正交虚线，并明确写出“下一阶段”或“尚未开展”。
- 箭头必须从框体边缘起止，不能穿过文字、框体或其他箭头。
- 相邻主节点之间至少保留约 0.7 cm 空白。
- 任何图形、文字和箭头不得发生覆盖；紧凑只能通过删减次要文字和优化分组实现，不能通过缩小字号实现。
- 每张中央图最多设置四个一级阅读区域；更细的步骤必须收进一级区域内部，不能继续横向增加同级流程框。
- 内部字段优先使用 2—6 个汉字或一个短术语；完整解释放在“主要难点”“方法 / 创新”或讲稿中。
- 局部放大区最多保留六个结构字段；实验结果区最多保留两组代表性数字，避免不同目标和统计单位混排。
- 同一信息只在最相关的任务页出现，例如 OracleIR 字段只在任务一展开，rosbag、ULG 和真值只在任务三展开。
- 若渲染后内部字段需要小于 15 pt 才能放下，优先删除次要字段或合并分组，不允许继续缩小字号。

中央图优先以 SVG 插入；若 LibreOffice 导出后出现 SVG 字体或布局异常，则 PPT 中使用高分辨率 PNG，并在 `assets/` 中保留同版 SVG。

## 5. 第 2 部分：任务与指标完成情况

### 5.1 表格结构

总标题建议为：

> 课题：具身智能系统控制逻辑漏洞挖掘技术研究

### 5.2 六项指标内容

#### 指标 1：语义 Oracle 构建

- 原始基线：少量目标专用手写 Oracle，缺少统一的多源规范处理和结构化中间表示。
- 开题要求：提取控制语义约束不少于 50 条。
- 当前指标状态：达到数量规模。已形成从多源规范、SpecBlock、OracleIR 到目标 Oracle 的处理链路；处理 425 个输入文件，得到 2749 个 SpecBlock、151 份现代 OracleIR，另有 35 份 legacy 逻辑规格。逐条 IR 与在线话题、字段和函数的映射仍待固化。

#### 指标 2：四类测试输入

- 原始基线：具备通用 ROS 消息变异和基础 Campaign，尚未形成完整的四维语义输入体系。
- 开题要求：输入包含用户指令、传感器数据、控制参数和消息事件四类。
- 当前指标状态：部分达到。用户指令覆盖较强，控制参数达到中等成熟度；已部分支持持续、频率、顺序、模式切换和反向变化等消息事件。IMU、LiDAR 等传感器目前主要用于 Oracle 观测，专用连续扰动和通用延迟、丢包、乱序仍偏弱。

#### 指标 3：语义变异算子

- 原始基线：原始方案以字段级随机或确定性变异为主，行为时间语义和物理耦合有限。
- 开题要求：语义相关变异算子不少于 5 类。
- 当前指标状态：达到，共 8 类。已形成多轴协同、方向翻转、持续块、边界推进、反转、轨迹弧、单点极值和回环八类跨目标语义策略；随机策略只作为探索兜底。后续仍需补充算子级消融和独立贡献分析。

#### 指标 4：偏轨判定与场景回溯

- 原始基线：具备基础 checker、rosbag 和 replay 能力，但控制语义和证据归并不足。
- 开题要求：支持控制语义偏轨判定与场景回溯验证功能。
- 当前指标状态：仿真侧达到。已在五类现代目标建立运行时 Oracle，并形成 rosbag、PX4 ULG、Gazebo 独立真值、输入恢复、离线复算和回放证据链，可按触发输入、发生时刻和控制链传播关系归并候选根因。Go2、ECO65-B 实物重复执行和虚实差分尚未开展。

#### 指标 5：语义约束覆盖率

- 原始基线：尚无统一的语义约束覆盖率定义、分母和同预算对照流程。
- 开题要求：相较 RoboFuzz，控制语义约束覆盖率提升不少于 20%。
- 当前指标状态：待形成正式证据。TB4 组合优化中唯一输入签名由 629 增至 842，增加约 33.9%；最高单一输入签名重复次数由 156 降至 21，下降约 86.5%，显示探索多样性有所改善。该结果不是语义约束覆盖率，也不是单变量消融；仍需完成同镜像、同场景、同预算的基线和统一分母计算。

#### 指标 6：平台与漏洞成果

- 原始基线：无本人可核实的实物验证闭环和 CNVD/CNNVD 正式编号基线。
- 开题要求：至少 2 类典型平台、未公开漏洞不少于 5 个，并获得 CNVD 或 CNNVD 编号。
- 当前指标状态：待形成正式证据。已在移动机器人、无人机、机械臂和 SLAM 软件栈形成高信号候选并开展公开沟通；截至 2026-09-17 共提交 34 条公开 Issue，其中 22 条 Open、12 条 Closed。Issue 不等于独立或确认漏洞；指定实物验证、未公开漏洞认定和正式编号尚未闭环。

表格页脚统一写明：

> 统计截至 2026-09-17；状态采用离散证据等级，不代表完成百分比。34 条 Issue 不等于 34 个漏洞；SpecBlock 和 IR 数量也不等于全部在线执行。

## 6. 第 3 部分：三项重点技术任务

三项任务严格对应书面开题报告的三条技术路线：

1. 定义正确行为：规范驱动的语义约束提取与行为 Oracle 构建。
2. 激活异常路径：基于语义反馈的扰动输入生成与种子调度。
3. 验证行为偏轨：控制语义偏轨判定、证据回溯与根因归并。

Go2、ECO65-B 实物验证和仿真—实物差分不单独列为第四个任务，而是在任务三中以橙色虚线标注为下一阶段。

### 6.1 技术总览页

主要难点：

> 正确行为难定义、稀疏异常路径难激活、非崩溃偏轨难验证。

中央图不使用三个同级大框，而采用“左侧研究输入—中部三任务闭环—右侧技术资产—底部平台范围”的分层架构。图的有效尺寸约为 `30.5 cm × 10.2 cm`。

#### 左侧：研究输入

三个上下排列的直角框通过汇流线进入中部系统框：

1. `系统规范｜文档 · 配置 · 接口 · 源码`；
2. `目标系统｜话题 · 参数 · 状态机`；
3. `实验场景｜平台 · 任务 · 仿真环境`。

#### 中部：规范驱动的语义模糊测试闭环

中部浅色大框内按从左到右的方向设置三个任务区，每个任务区只保留三个一级步骤：

1. 任务一：`规范分块 → 结构化约束 → 运行时 Oracle`；
2. 任务二：`行为种子 → 语义变异 → 反馈调度`；
3. 任务三：`在线判定 → 复算回放 → 根因归并`。

三个任务区之间使用深蓝或黑色实线箭头，并在任务区上方分别标注 `定义正确行为`、`激活异常路径` 和 `验证行为偏轨`。

从任务三底部沿系统框外围返回任务一和任务二，使用绿色正交反馈线。反馈线在平台条上方单独预留约 `0.8 cm` 高的路由槽，不与平台条共用底边，线上只写：

> 补充规则 · 调整输入

这条反馈线表示验证结果可以完善规则并调整后续输入，不表示任务三的结果自动修改 Oracle 或种子。

#### 右侧：形成的技术资产

右侧使用四个短框，不使用长句：

1. `可追溯规则`；
2. `高价值种子`；
3. `候选证据包`；
4. `公开沟通材料`。

不在这一列使用“已发现漏洞”等表述。

#### 底部：当前平台范围

系统框底部设置一条窄的平台条：

> PX4　TurtleBot4　MoveIt2　SLAM　Nav2

平台条右侧标注：

> 五类仿真目标已接入｜成熟度不一

平台条下方的边界说明为：

> 当前已形成跨目标仿真侧原型

Go2 和 ECO65-B 不进入当前平台条，只在任务三页面的下一阶段分支中出现。

方法与创新文案：

> 先从系统规范中明确机器人在不同状态下应当怎样响应，再生成带有控制语义的测试输入，最后结合仿真记录和回放结果确认异常是否稳定存在。

> 把前述工作接成一个能够相互反馈的测试流程：验证阶段发现的问题可以反过来补充规则并调整后续输入，使测试不只是增加轮次，而是逐步逼近真正有价值的问题。

页面边界说明：

> 当前已形成跨目标仿真侧原型，不同目标成熟度不一；实物差分与正式漏洞编号为下一阶段。

### 6.2 任务一：规范驱动的语义约束提取与行为 Oracle 构建

主要难点：

> 建模难：多源规范异构、跨模块约束隐含，难以形成可执行且可追溯的行为判据。

中央图使用“约 70% 主架构 + 约 30% OracleIR 局部放大”的左右结构。主图上部表达正向构建，底部使用独立追溯带表达反向追溯；两条路径不交叉。

#### 左侧主架构：规范到运行时判断

第一组为 `① 多源规范`，内部使用 2×2 小框：

- `文档 / 注释`；
- `配置 / Launch`；
- `ROS 接口`；
- `源码 / 模型`。

模块角标为 `425 个输入文件`。无需在主图逐项列出八种文件扩展名。主架构顶部统一标注 `当前工作区 · 五个现代目标`，该限定同时适用于 425、2749 和 151 三组数字。

第二组为 `② 格式感知预处理`，内部按纵向使用三个短步骤：

> 格式识别 → 分块 / 归一 → 保留来源

输出框为：

> SpecBlock<br>
> 内容 · 路径 · 上下文

该框角标为 `2749 个规范块`。

第三组为 `③ Agent 候选约束生成`，内部步骤为：

> 检索相关规范 → 生成候选 IR → 结构校验 / 语义规则检查

从“结构校验 / 语义规则检查”使用一条细回路返回“生成候选 IR”，线上只写 `失败则修订`。输出框为 `OracleIR`，角标为 `151 份现代 OracleIR`，不写成“151 条已执行 Oracle”。

第三组和第四组之间设置橙色竖向虚线并标注 `自动化边界`。虚线两侧分别标注：

- 左侧：`Agent：检索 · 生成 · 校验`；
- 右侧：`Agent + 人工：绑定 · 审查`。

第四组为 `④ 目标上下文化与判断`，内部使用 2×2 四个短框：

- `话题 / 字段绑定`；
- `状态 / 时间窗`；
- `容差 / 噪声`；
- `质量门控`。

四个上下文条件汇入 `运行时判断`，再输出三个互斥状态：

> 正常　偏轨　不可判定

`不可判定`使用灰色，表示数据不足、任务未真正执行或基础设施异常时不直接报告目标漏洞。

#### 右侧局部放大：OracleIR 的关键字段

右侧面板标题为 `OracleIR｜关键字段`，内部使用 2×3 六个直角字段框：

| 易懂问题 | 结构化内容 |
|---|---|
| 看什么 | 观察量 |
| 阈值从哪来 | 参数 / 单位 |
| 怎么算 | 派生量 |
| 何时算错 | 断言 |
| 何时生效 | 作用域 |
| 看多久 | 时间窗 |

面板底部设置来源条：

> 来源证据：SpecBlock ID

主流程中的 `OracleIR` 与右侧面板之间使用细虚线或放大括号，不使用粗实线箭头，因为右侧是局部解释而非新的处理步骤。

#### 底部反向追溯带

底部使用由右向左的绿色或蓝绿色正交箭头：

> 原始文件 / 章节 / 参数路径 ← SpecBlock ← OracleIR ← 运行时规则 ← 判定证据

这条路径只表达证据追溯，不返回 Agent 自动修改约束。

方法与创新文案：

> 先按文件类型分别处理 Launch、YAML、接口、源码和说明文档，把与控制行为有关的内容整理成能够追溯到原文的规范片段，再据此生成结构化约束。

> 生成 Oracle 时，先找到与当前行为有关的规范，再检查字段、单位、适用状态和时间条件；对于依赖具体话题或状态机的规则，再结合目标系统补充上下文，避免把模型生成内容直接当作最终判断代码。
